Why law-powers

AI 很會寫，卻不代表它真的懂法律

這個專案不是從產品會議開始，而是從一場真實的應訴經驗開始。

“

案件最後雖然全勝，但 AI 寫出的訴狀與法律文件，曾經漏洞百出。

當爭議金額不高、請律師的成本可能超過案件本身，自己研究似乎是合理選擇。真正開始之後才發現：AI 可以幾秒鐘生成一份看似完整的答辯，但不存在的判決、錯置的裁判意旨與失準的台灣法律用語，都必須自己一筆一筆查。

再三要求檢查，幻覺仍然存在

模型的自信不是證據。沒有外部資料來源，它只是在重新組織自己的猜測。

一般人不知道法院使用什麼詞

口語案情與裁判用語之間存在落差，光是找到正確搜尋詞就可能耗掉數個晚上。

找到判決，不代表真的讀懂

還要分辨法院見解、當事人主張、上下審結果，以及裁判是否已被廢棄。

Seven focused skills

從一團混亂的案情，到可查證的法律文件

每項技能只負責一件事，避免在同一個 Prompt 裡混合研究、策略、視覺化與文字校訂。

01 / LEGAL-BRAINSTORMING

先把事實、爭點與證據缺口問清楚

在起草書狀以前，逐步整理當事人、時間序、法律關係、對造可能主張與現有證據，避免 AI 在事實不明時搶著下結論。

facts → issues → claims → defenses → evidence gaps
02 / LEGAL-RESEARCH

雙軌法源檢索

語意找論理、關鍵字找原文，合併後再逐筆驗證引用資格。

03 / ELEMENT-ANALYSIS

構成要件涵攝

把法條拆成一項項要件逐一對映本案事實：該當○、不該當✗、事實不明△——△ 直接轉成證據需求清單，不以推測補充事實。

04 / LEGAL-GRAPH

法律關係圖

將事實、法條、判決、爭點、當事人與證據整理成可互動檢視的關係圖。

05 / COMPLIANCE

契約與合規稽核

辨識條款風險、權利義務不對等、法規缺口及需要補強的約定。

06 / WRITING-HUMANIZER

台灣法律文字校訂

移除 AI 痕跡與中國大陸法律用語，同時凍結日期、金額、請求、抗辯與引用，不因潤稿改變法律效果。

07 / OFFICIAL-DOCUMENT

政府公文書撰寫

函、書函、公告、簽的段落結構與稱謂、期望目的語，依《文書處理手冊》套用；先判對行文方向（上行／平行／下行），用語才不會全盤用錯。

主旨 → 說明 → 辦法（函）／擬辦（簽）

Usage examples

一句話的委託，換一條可查證的工作流

三種典型情境：訴訟主線、契約支線與公文輔助——每一步引用什麼、缺什麼證據，都交代得清楚。

CASE 01 / 車禍求償
「我騎機車被闖紅燈的計程車撞傷，警方初判表認定對方過失，但我還沒拿到診斷證明書。可以向誰求償？勝算如何？」

梳理案情後雙軌檢索靠行連帶責任判例，將《民法》第 184 條拆成六項要件逐一涵攝——「損害」與「因果關係」因缺診斷證明書標 △，直接轉成證據補齊清單，並提示第 188 條、第 191 條之 2 備位主張。

brainstorming → research → element-analysis → graph
CASE 02 / 契約審查
「附上我們要簽的軟體委託開發契約草稿，幫我審查風險、標出需要重談的條款。」

逐條標示紅／黃／綠風險與修改建議，建立契約→條款→義務三層關係圖並依風險上色，最後把修約說明校訂成自然的台灣法律語體。

compliance → graph → writing-humanizer
CASE 03 / 公文撰擬
「公司要發函向主管機關詢問法規適用疑義，幫我擬一份函稿。」

先判斷行文方向（上行／平行／下行），再套用「主旨／說明／辦法」段落結構與正確稱謂、期望目的語；引用的法規字號一律先經檢索查證，不憑記憶杜撰。

official-document →（法源查證）research

3D graph how-to

四個步驟，把案件變成一張 3D 法律關係圖

不需要伺服器與帳號：Agent 負責產資料，瀏覽器直接開頁面，離線也能檢視。

HOW-TO / 操作步驟

從案情到 3D 圖譜

  1. 01
    對 Agent 下產圖指令

    例：「幫我把這個案件的事實、法條、判決與爭點整理成法律關係圖」，legal-graph 會組裝 superset 格式的節點與連線資料。

  2. 02
    Agent 將資料寫入 data.js

    完整開發專案寫在專案根目錄；skills-only 安裝寫在 skills/legal-graph/renderer/data.js——與 index.html 同組即可。

  3. 03
    瀏覽器開啟同組 index.html

    頁面自動讀取 window.GRAPH_DATA 渲染 3D 圖譜（需支援 WebGL）；自包含單檔、離線可用。

  4. 04
    互動檢視與更新

    拖曳旋轉、滾輪縮放、點節點看詳情（勝敗徽章／條款風險／要件該當性）、依節點類型篩選；換案件時以新資料覆寫 data.js 再重新整理。

DATA / 資料格式

data.js 只有一條規則

window.GRAPH_DATA = {
  "nodes": [ ... ],
  "edges": [ ... ]
};

保留這個格式，其餘交給技能：節點分 11 類（事實、法條、判決、爭點、當事人、證據、契約、條款、義務、要件⋯⋯）、連線分 17 種語意類型，圖例與配色由渲染器自動分流。

查證紀律不因視覺化而放鬆——判決引用先經 legal-research 驗證、要件該當性（met）來自涵攝表、條款風險（risk）來自合規審查報告，legal-graph 只彙整、不臆測。

Offense & defense

不是替你喊得更大聲，而是幫你找到能站得住腳的位置

同一套查證流程，同時服務於提出主張與拆解對方主張。

OFFENSE / 進攻面

把主張建立在要件與證據上

  1. 01
    建立請求權基礎

    從事實反推可能適用的法律關係與構成要件。

  2. 02
    尋找相似裁判論理

    比較法院在類似事實中如何評價行為、契約與證據。

  3. 03
    預演對造抗辯

    在提出主張前先檢查時效、舉證與程序上的弱點。

DEFENSE / 防守面

逐項拆解對方是否真的證明

  1. 01
    檢查法律要件

    分辨對方只是陳述故事，還是真的滿足每一項構成要件。

  2. 02
    攻擊證據鏈缺口

    確認來源、時間、同一性、證明力與待證事實能否接得起來。

  3. 03
    驗證對方引用

    檢查判決是否相關、見解是否被誤讀，以及是否已遭上級審廢棄。

Honest by design

它不能保證勝訴，也不會取代律師

法律結果取決於事實、證據、程序與法院判斷。law-powers 的目標不是製造勝訴承諾，而是降低研究成本與引用幻覺，讓每個論點更容易被人類重新檢查。

查無資料，就明確說查無資料不以語氣自信填補證據空白，也不捏造法條或裁判字號。
裁判片段只是線索，不等於法律結論重要主張仍須閱讀全文，區分法院見解與當事人陳述。
期限與高風險程序，仍應尋求專業協助遇到上訴、強制代理或重大財產與人身風險，應諮詢中華民國執業律師。
